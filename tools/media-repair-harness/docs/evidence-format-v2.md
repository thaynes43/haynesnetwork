# Evidence format v2, guards v3 and the audit bug fixes (W18)

Owner: OpenProject story [#144](https://work.haynesnetwork.com/work_packages/144) (epic #48). Source: the Astra audit of the dev-c4 evidence and instructions (#143, sections 2 and 3, items P0) and
its review. Everything here is **opt-in**: with the new options unset, every request, run record and scorer-read field is what `origin/main` 7abf11fb produced
(`tests/testdata/legacy-e2e-golden.json`, the replay-identity golden and the prompt and schema digests). `HARNESS_VERSION` stayed `dev-c4` in that change; W19 bumped it to `dev-c5` and added prompt v5, which is valid only with this format.

## Options and the versions they select

| Option | Selects | Valid with |
|---|---|---|
| `--evidence-format v2` | evidence format v2 (typed layer, capabilities, pagination), **tools behaviour v2** (bugs a, d, e), **audit v2** (bug b) | prompt `v4` or `v5` (`v5` requires it); guards off or `--guards v3` |
| `--guards v3` | G-healthy v3 (bug c); G-write as in v2 | any prompt, with or without the format |

Anything else that uses a new option is refused up front with an explicit message (`run.check_option_combination`): `--evidence-format v2` with prompt v1, v2 or v3, and with `--guards v1` or `v2`. Unknown values are refused by the parser.
The manifest `config` (and so `config_hash`) gains `evidence_format`, `tools_behavior`, `audit_version`, `page_contract` and `wire_bytes` only when the format is on, and `guards: "v3"` when guards v3 is on; an unset run keeps the earlier config shape.
The run record gains `evidence_format{version, page_contract, wire_bytes, tools_behavior, audit_version, capabilities, messages[], final_summary}` and `action_audit.audit_version` only for a v2 run, and
`tool_calls[].raw_output` (the uncut redacted text the typed layer was derived from) when the format is v2 or guards are v3. `run_summary.json` gains `evidence_format`.

## The five audit bugs, each fixed under a version (the earlier behaviour stays under the earlier version)

| Bug | Earlier behaviour (kept for v1) | Fixed behaviour |
|---|---|---|
| a. `decode_sample(full=true)` | local and remote fallback ran a 4 s window and called it full | **tools v2**: local runs a real full decode of the first video and first audio stream inside the existing 25 s limit (`window_s: "full"`, `completed_to_eof`); at the limit it returns status `partial` with the window that actually ran, `completed_to_eof: false` and `request_unmet`. Remote cannot (8 MiB, 25 s): status `partial`, the 4 s window, `request_unmet`. A replay without a recorded full decode is `unavailable`, not a crash. No limit is raised |
| b. `audit.compute` `full_decode_ok` | true when a full-argument call returned `ok` | **audit v2**: true only on affirmative completion evidence -- an exit-0 full decode whose decoded span reaches the KNOWN container duration (a tool's own `completed_to_eof: true` is a claim that is checked against the span; an unknown duration or span leaves completion unknown) -- a clean result, no unmet request and a **recorded stream scope**; absent proof is not met, with the reason in `detail`. A result is a full decode only when it says so (`window_s: "full"`); a request for one proves nothing |
| c. G-healthy | presence of any `ok` integrity result | **guards v3**: all shown evidence and tool results are examined, read through the SAME text the model saw (the bounded `output` in the legacy format, never `raw_output`); a known integrity defect contradicts healthy even next to clean results (order independent); an `ok` result that reports a defect is not clean; unknown fields are neither clean nor damaged; an EPUB collector's `valid:false` vetoes healthy; no clean integrity result still abstains. The reason names the finding, its kind and location and the observation id; the model's decision stays in `guard.applied[].original`. A guard can only turn a decision into `insufficient_evidence` / `escalate` and never infers whole-file health from a clean sample |
| d. `live_tool` truncation flag | the collector's flag was dropped | **tools v2**: kept (`truncated: true`, `collector_truncated`) |
| e. sampled coverage | overlapping windows were added up (`sampled_fraction` 1.5 on an 8 s file) | **tools v2**: the union of the windows, clipped to the duration; `decoded_s_total_windows` keeps the sum |

## What the model sees under `--evidence-format v2`

The typed layer (`evidence_v2.py`) is a deterministic function of **model-visible observations only**: an `Observation` is `{id, tool, args, status, output, backend, source, collector_truncated}` and the
case context the model already sees. The case object is never passed in, so no truth, accepted class, supported action, solvability, family, correction, provenance, outcome step, injection flag or
fixture path can reach the output; the harness-side `injected` backend marker is dropped, so no backend is shown for such a result. Args echoed back are limited to known numeric/boolean options and a frame handle (`run.safe_args`).

First message: `case_id, media_type, context, tools_available, tool_call_budget, capabilities, evidence_format, evidence`. `evidence` = `{alerts, [page], items, facts, coverage, client_comparison}`.
Tool reply: the same envelope keys as before (`type, id, tool, status, truncated, output, tool_calls_remaining`); `output` is a nested object, not JSON in a string.

* **Per result**: `execution` (`state` ran / failed / timed_out / unavailable, the raw `status`, `cause` input / tool / unknown for failures, `completion` complete / partial / none, `output_truncated`, `reason`);
  `findings` (`kind`, `known_defect`, `location`, raw-excerpt `detail`, `src`); `scope` (requested against completed: window, offsets, `to_end_of_file`, streams, stages, intervals); `unresolved`; `conflicts` (a status `ok` with a defect, exit 0 with decoder errors, a request not honored, a decoded span shorter than the container duration, two different container durations); `facts` (compact parse, units in the key names: `_s`, `_bytes`, `_bps`, `_hz`, `_px`).
  `ok` never implies a clean file; a collection failure never implies a defect; a non-zero exit alone and any unrecognised error text stay `known_defect: false`. Recognised damage wording is a small general libav / package list (`DAMAGE_RX`), not a case list.
* **Alerts** come first: conflicts, then known defects, then execution failures, one short entry each naming the id of its detail. They are repeated on every page and never dropped to fit.
* **Coverage matrix** (`coverage`): container; time intervals per stream (the union of the windows that name the stream, damaged overriding clean in an overlap, clipped to the known duration, `unknown` when the duration or the stream selection is not recorded); the stream list with a decode state; chapters (`clean`, `damaged`, `partly_checked`, `not_checked`); EPUB package stages in the inspector's order. It describes checks performed, never a diagnosis or a "representative enough" verdict. It is recomputed from the observations shown so far and appears in a reply only when it changed.
* **Client comparison** (`client_comparison`): only when the case **states** a client (`context.client_profile` or `context.expected.client_profile`; a structured profile or the prose forms, e.g. "h264, 8-bit yuv420p, up to 1080p"). Each selected stream field (container, codec, bit depth, pixel format, resolution, audio codec, channels, layout) is `supported` / `unsupported` / `unknown`; the stream selection is stated (`recorded`, `only_stream_of_type`, `ambiguous`; an ambiguous or unrecorded selection cannot support an overall claim); profile fields that are not read are listed. No client is inferred and incompatibility is not damage.
* **Capabilities** (`capabilities`, per offered tool): backend (`replay`, `pinned_replay`, `local`, `remote`, `live`, `stub`), availability before the call, recorded offsets, window length, and whether a full decode exists (`recorded`, `not_recorded`, `bounded run`, `not_possible`). It reads which offsets exist and never a recorded result.
* **Pagination (`pages-v1`)**: every message is at most 8192 UTF-8 bytes (the first message's `evidence` block, and each tool reply as a whole, budget notice included). A page is the repeated header (identity, alerts, execution) plus whole units in priority order, never a structure cut in the middle; a split list says `"<field>_shown": "n of N"`; a unit too large for any page is replaced by a marker in `page.oversize`; long strings are cut with `...[+N chars not shown]`. `page` = `{contract, source, n, of, next, next_costs_tool_call, elsewhere, conflicts_total}`. `next` is an opaque stable cursor that embeds the case alias (another case's cursor does not resolve); fetching it is a tool call `{"tool": "<an offered tool>", "args": {"cursor": "..."}}` that **uses one of the 6 calls** (recorded as `tool: "page"`, `continuation: true`, never an observation for the guards). A case that offers no tool cannot page: the first page says so (`page.retrieval`) and keeps the counts and alerts. `truncated` in the envelope means the tool or collector cut its own output; pagination is not truncation.
* A decision may cite a finding id (`t2.f1`); the record credits its observation (`t2`) and stores the decision as written.

## Limits and deferrals

* Not in W18: the identity comparison table and the ordering / edition table (audit P1), richer content inspection (EPUB body, audiobook speech), prompt v5 (it must define the new fields and pagination and keep the schema contract) and every model run. They belong to W19 / dev-c5.
* The replay recordings state no stream selection for a decode window, so decode intervals of replay data sit in the `unrecorded` row, per-stream decode states are `unknown`, and `full_decode_ok` (audit v2) is not met for them. Filling that gap needs new recordings.
* Prose client profiles are read by a fixed grammar (video and audio codec lists, `N-bit`, pixel format, `up to Np`, `up to N channels`); anything it does not read is listed under `not_compared`, not guessed. Profile and HDR fields are not compared.
* The container duration is taken from the first `ok` probe-type result; the decoded-span check uses a single one-second allowance (`EOF_TOLERANCE_S`) for container rounding and unequal stream lengths.
* Guards v3 on an old record (`mrh-guard --guards v3`) reads the stored `output`, which the legacy format cut at 8 KiB; a cut that breaks the JSON is `unknown`, never clean or damaged.
* The coverage and client sections repeat in a reply when they change, which costs context on small local models; the size is bounded by the 8 KiB envelope, and a reply that does not fit pages them.
* Excluded volatile record fields in the compatibility golden: `started_at`, every `wall` / `wall_s` / `elapsed_s`, `harness_git_sha`; a live collector's clock is fixed in the golden so `elapsed_s` is stable.

## Review fixes (PR #1023, Astra 3 and the independent review)

* **Unknown stays unknown.** A defect is only a positive, recognised observation (libav damage wording in `DAMAGE_RX`, a package stage failure, a collector's `cause: input`); other decoder or probe text is `decoder_messages_unclassified` / `probe_messages` with `known_defect: false`, an `unclassified` interval, and integrity `unknown`. Clean needs a positive observation: an `ok` probe needs a parsed container and streams (an empty `{}` is unknown); a decode needs exit 0, a present blank stderr and frames, a decoded span or bytes read. A run that failed, timed out or never ran certifies nothing clean. A plain-text integrity output is kept as `facts.raw`; only explicit damage wording in it is a defect (the harness's own cut markers are removed first).
* **Live book collectors.** The real EPUB schema (`valid`, `stages_passed`, `stage`/`error`, `dc_*`, `findings[{severity, what}]`) and audiobook schema (`files[]` with format, tags, streams, chapters, per-part decode windows, probe state, `tag_consistency`) are normalised; facts are kept, recognised damage is a defect, `valid:false` vetoes healthy, decode windows are per part (`coverage.parts`), not on one timeline.
* **Guards and capabilities read only what is shown.** `raw_output` is kept for format v2 only (its typed pages carry the whole text); the legacy format with guards v3 reads the shown, bounded text. The capability advertisement is built from operation metadata (which recordings, offsets, ranges and keys exist), never from an uncalled result; `ocr` lists `recorded_reading_ranges_s`, which discloses where a reading is recorded, not what it says.
* **Client grammar.** Prose is read only when every word is recognised (codec names, `N-bit`, a pixel format, `up to Np`, `up to N channels`, `or`/`and`); `only`, `no`, `not`, `except` and any other word make the clause unread (listed in `not_compared`, nothing compared). `video_profiles` / `audio_profiles` (structured) compare the codec profile. `summary.complete` is true only when every stated field was compared with a known verdict, the selection is unambiguous, the container was compared and no statement went unread; it never means the file will play.
* **One reference resolver** (`run.make_resolver`): an observation id, or a finding / conflict id that was actually emitted (`t1.f1`), resolves to its observation; `t1.nonexistent` stays a bad reference. The guards and the record use it; the decision is stored as written.
* **Pagination keeps everything retrievable.** A long string keeps its first 400 characters and a pointer (`...[+N chars: detail <id>]`); the whole text is a `details` unit on a later page. Large structures are split into units of at most 2400 bytes, never dropped. The first message is budgeted as a whole (context and capabilities included); every stored page is sized against the worst-case fetch envelope (longest offered tool name, the sixth call, the budget notice). `page` carries `alerts_total` and `conflicts_total` (the true conflict count). `--tool-output-bytes` is the page budget under format v2 (2048 to 8192, recorded as `wire_bytes`).
* **Chapter coverage is per stream** (`by_stream`); there is no combined chapter label.
* The wiring-smoke bundle is gzip (no lzma dependency in the Job image), capped at 240000 bytes in total because client-side `kubectl apply` stores the manifest in an annotation limited to 262144 bytes.

## Second fix pass (Astra 4 and the re-review of 5a576d70)

* **Damage wording only in diagnostics.** `damage_wording()` is applied to decoder / probe stderr, an inspector's error message and a collector's error lines, never to titles, tags, chapter names, paths or the harness's own notes. File names and paths inside a diagnostic are removed first and a negated mention ("no corrupt frames found") is not damage. Unparsed (cut) JSON contributes only the values of its diagnostic keys (`stderr`, `error`, ...); plain text is the tool's own message. A permission or other execution error that mentions `corrupt.mkv` is an execution failure (`cause: tool`). Generic words (`truncated`, `end of file`, `damaged`, `corrupt` alone) are no longer in the list.
* **Live full decode** uses the same affirmative check as every backend: a decoded span that reaches the known duration (the collector's own, or another shown result's); a shorter span is `decoded_span_shorter_than_duration`, an unknown span or duration leaves completion unknown.
* **Client grammar is structural.** A bit depth or pixel format belongs to the codec it follows and is applied to that codec; one that precedes every codec ("8-bit hevc"), a second `up to` limit or any unknown word makes the clause unread, so a recognised token is always used in a comparison or the clause is not read.
* **One resolver everywhere**: `evidence_v2.reference_resolver` is used by the runner, `decision_guard.apply` (online and offline), `apply_to_record` and `--restore`; the offline path recomputes the emitted finding ids from the record's own observations, uses audit v2 and raw evidence for v2 records.
* **Pagination**: list elements keep their index (`_i`) when an element is split; unit, chunk and string limits scale with the page budget (`Limits`); a message that cannot fit (an oversized context, or a unit that cannot fit a page) raises `PageBudgetError`, which the runner records as a harness error, so nothing is ever sent over the limit; the `elsewhere` counts are grouped by section so the page object stays small; under tools v2 the live collector is cut at the raw cap, not at the page budget.
* **Raw diagnostics** are all kept in `facts.diagnostics` (one entry per collector message, classified or not); a timeout keeps the windows its output shows (it certifies nothing as a whole); an EPUB `valid:false` veto is a `collector_verdict` alert (`known_defect: false`, `vetoes: healthy`), distinct from a `defect`.

## Third fix pass (Astra 5 and the re-review of 4328e342)

(The allow-list table below is the third-pass list; the fourth pass revised it, see the tables at the end of this document.)

* **Damage recognition is a positive allow-list** (`DAMAGE_ALLOW_LIST`), replacing the negation heuristic. A diagnostic LINE (decoder / probe stderr, an inspector's error, a collector's error line; cut JSON contributes only the values of its `stderr` / `error` keys) is damage only if, after its decoration is stripped (`[name @ 0x...]`, `pipe:N:`, `in#N`, `<input>:`, a file path, an exception type, an ffmpeg wrapper such as `Error while decoding stream #0:0:`), it STARTS with one of the fixed messages below. Each line is classified on its own, so a permission line, a title or a note can never erase a damage line elsewhere. Anything unmatched is `unclassified`: kept in `facts.diagnostics`, integrity unknown. There is no negation logic and no bare-word matching ("corrupt frames: 0" and "pipe:0: Invalid data found" both come out right by construction). * `Permission denied`
* `No such file or directory`
* `Operation not permitted`
* `Input/output error`
* `Cannot allocate memory`

* **Live probe stderr** (and each audiobook part's `probe_stderr`, and the record-level excerpt) goes through the same matcher: an `ok` probe with `File ended prematurely` on stderr is damaged, with other text unknown, never clean; every line is kept in `facts.diagnostics` with its class.
* **Pagination no longer crashes on a splittable unit.** When the alerts alone would not fit they are shortened in two steps (one short string each, then grouped by type and kind with the first ids, the full id lists retrievable as `alert_ids` units); a unit that does not fit the space left is divided further (an element of a list keeps its `_i` index); `elsewhere` is grouped by section (`details`, `alert_ids` are one key each); with no tool offered the `retrieval` sentence is counted in the budget. * **Timeout wording** separates the windows the call observed from the unfinished remainder.

## Fourth fix pass (Astra 4-6 and the re-review of 3ffd3ece)

* **Per-element classification.** The messages a collector reports as an array (`segments[].errors`, an audiobook part's `error_lines`, an audio segment's `problems`) are never joined before classification: every element, and every line of every element, is classified on its own. The order of the array cannot change the verdict (permutation tests over the decode, audiobook and audio arrays). The one cross-line rule: an `error reading header` line directly followed by an execution-error line (for example `Input/output error`) is itself an execution failure; alone it is a `decoder_warning`.
* **File names do not spell messages.** A recognised `<path or file name>:` prefix is stripped, and a message is matched at BOTH ends: after the message only an optional full stop, or its documented continuation (`: line N, column N`, `at pos. N (0xN)`), is allowed. `moov atom not found.mkv: Permission denied` and `File is not a zip file.epub: Permission denied` are execution failures; `moov atom not found in the cache directory` matches nothing.
* **A new class, `decoder_warning`.** A message real decoders also print for healthy or merely unusual files, or one that names a failed operation without a cause. It is not clean, not a known defect (`known_defect: false`, finding kind `decoder_warning`), integrity stays unknown, it never vetoes healthy on its own (a real damage line still does), and it stays in `facts.diagnostics` with class `warning`. Moved to it: `Invalid data found when processing input` under a decode wrapper (`Error while decoding stream #0:0:`, `Decoding error:`; it stays damage when bare, after `pipe:N:` or a file name, or after `Error opening input files:` / `Error during demuxing:`), `non-existing PPS`, `missing picture in access unit`, `Element at ... exceeds containing master element`, `Could not find codec parameters` (also printed for healthy PGS subtitle streams) and `error reading header`.
* **Allow-list corrections.** `concealing`, `corrupt input packet` and `Packet corrupt` stay but are marked "not emitted at the collectors' log level (-v error)"; `Packet corrupt` is attributed to libavformat/demux.c; `corrupt decoded frame` is accepted with or without `in stream N`. Added (sourceable messages only): zipfile `File name in directory ... and header ... differ`; zlib `Error -3 while decompressing data` (and the truncated-stream text of -5; -4 is an execution failure, other codes are unclassified); expat `duplicate attribute`, `undefined entity`, `unbound prefix`; execution errors `Stale file handle`, `Transport endpoint is not connected`, `Connection timed out`; a small set of HEVC / AAC / AC3 / FLAC decoder messages as warnings (FFmpeg source templates, not checked against a binary: none is installed on the pod). The tests build the Python and expat texts from real in-memory exceptions.
* **Split elements keep their own index.** `_split_further` indexes every sibling of a list once any is divided (the position among ALL elements, already-divided ones included), so two divided siblings can no longer both read `_i = 0` and merge.
* **One page, no retrieval text.** The sentence that tells a model without tools that the rest is not retrievable is added only when the evidence takes more than one page. A first message that fits one page has no `page` object and no sentence (the 22 public no-tools first messages do not change).
* **A stated bit depth is a maximum.** "hevc 10-bit" and "hevc up to 1080p, 10-bit" support an 8-bit file and reject a 12-bit one.
* **An EPUB execution failure is checked before the stage.** A local `PermissionError` / `OSError` at `zip_open` is `cause: tool` (package stages unknown, no `package_error` finding); a `BadZipFile` at the same stage stays damage.
* **The full alerts take at most a quarter of a page** (budget // 4); otherwise they are shortened in tiers and the rest stays retrievable as `alert_ids`. A live 25-part audiobook with a defect in every decode window needs 12 pages at 8192 bytes and 28 at 4096.
* **`PageBudgetError` over both public dev suites** (first message and default replies of every case): 0 at 8192 and 0 at 2560.

## Page fetches carry their origin

A page fetch is stored in `tool_calls` as `tool: page`, `continuation: true`, and now `pages_of` (always a list: the id of the observation it pages, or every case-evidence id for the pages of the first message) with the origin's own `status` (the first one that is not ok when several), never a stamped ok. The one reference resolver (`evidence_v2.reference_resolver`, with `page_origin_map(tool_calls)`) and the audit map a cited page-call id to its origin(s), so `no_failed_tool_cited`, `cited_evidence_supports`, `refs_to_non_ok_tools` and G-write v3 read the origin's real status online, in `mrh-guard`, `apply_to_record` and `--restore`. ## Gate fix (OpenProject #148)

* **Support comes from the typed layer (guards v3, audit v2).** An `error` result supports a write only when its typed execution cause is not `tool` AND it carries a positive damage finding (a known defect). ## Diagnostic rules diag-2 and tools behaviour v4 (W25, OpenProject #156; opt-in, offline)

Both are new versions; nothing above changes. Every configuration the runner can select, every record and every committed result reads **diagnostic rules `diag-1`** (the allow-lists and stage shapes above, byte for byte) and tools behaviour v1, v2 or v3. The new versions are selected programmatically (`evidence_v2.diagnostic_rules('diag-2')`, a context manager; `tools.Context(..., tools_behavior='v4')`) by the offline scripts (`scripts/w25_deltas.py`, `scripts/contract_v3_tension.py --diagnostic-rules diag-2`). No runner option selects them yet: a configuration with them is a later story with its own prompt and pre-registration.

**The pairing is fixed (W25b).** Tools behaviour v4 words results that only `diag-2` recognises (`the spine documents contain no text` is unclassified under `diag-1`, so an all-empty book would read as an unclassified failure). A `tools.Context` with `tools_behavior='v4'` is therefore refused (`ValueError`) unless it is built inside `diagnostic_rules('diag-2')` (`tools.TOOLS_V4_DIAGNOSTIC_RULES`), and the typed layer that reads its results must run under `diag-2` too. **The pairing is enforced only when the `Context` is built:** nothing checks the rules a caller classifies a v4 result under, so a v4 result classified under `diag-1` reads its v4-only wording as unclassified (never damage, never clean). `diag-1` stays byte-identical: no v4 wording was added to it. (W27: v4 also pairs with `diag-3`; why the pairing is not checked again at classification time is in the next section.)

**diag-2** corrects four defects in the typed layer's recognisers (`evidence_v2.py`, `DAMAGE_ALLOW_LIST_DIAG2`, `OPEN_TAIL_RX` with `_ends_in_exec`, `_zip_crc_readings`, `_EPUB_STAGE_SHAPES_DIAG2`):

| diag-1 pattern | diag-2 pattern | Why |
|---|---|---|
| `Bad CRC-32 for file .+` | `Bad CRC-32 for file ` + a Python `%r`-quoted name (`'...'` or `"..."`) | zipfile prints the name with `%r`; `.+` accepted `'a.xhtml': Permission denied` as damage |
| `CRC mismatch in member .+` | `CRC mismatch in member ` + a name (a leading space allowed) that does not END in an execution error | the harness's own message names the member unquoted; a trailing execution error is that error |
| `Corrupt (?:zip64 )?extra field.*` | `Corrupt extra field [0-9a-fA-F]{4} \(size=\d+\)` or `Corrupt zip64 extra field\. (?:File size\|Compress size\|Header offset) not found\.` | the two documented zipfile forms; `.*` accepted any tail |
| `manifest names \d+ member\(s\) that are not in the archive.*`, `manifest names members that are not in the archive: .+`, `manifest references missing member\(s\): .+` | the same, with a tail that does not END in an execution error | open tails: `...: Permission denied` was damage (W25b, Opus 2) |

"Ends in an execution error" (`_ENDS_IN_EXEC`) means: `: ` (or a line break) and then an execution-allow-listed message running to the end of the text, with the classifier's own decoration allowed in front of it: `<Name>Error: ` and `[Errno N] ` (`_OTHER_WRAPPER_RX`). So `: Permission denied`, `: [Errno 13] Permission denied`, `: PermissionError: [Errno 13] Permission denied: 'a.xhtml'` and `: MemoryError: <anything>` all count (W25b, Opus 2: the decorated forms were read as damage before).

* **A trailing execution error after an open-tail message is execution.** A diagnostic that starts with one of the six open-tail messages above (after the classifier's own decoration) and ends in an execution error (as defined above) is that execution error, checked before any damage reading (execution precedence). The end is judged on the COMPLETE diagnostic: `classify_line` checks the whole line before it clips its candidates to 1,000 characters, and `epub_failure` checks the whole error text before it splits it into lines (W25b round 2, AUDIT-ASTRA-40: `manifest references missing member(s): <1,020 characters>: PermissionError: [Errno 13] Permission denied` and `manifest references missing member(s): a<newline>b.epub: Permission denied` were damage that supported a write). The check (`_ends_in_exec`) gives the answer of the `_ENDS_IN_EXEC` regex in linear time: the regex is end-anchored and an execution message holds no line break, so only the messages on the last line are examined, each once forward and once backward (the regex itself backtracked quadratically on long runs of line breaks: about 72 s on a 65,535-character member name). So `CRC mismatch in member a.xhtml: Permission denied` and `CRC mismatch in member a.xhtml: MemoryError: Invalid data found when processing input` are tool failures (`cause: tool`), not defects. The claim is exactly that wide: only messages on the execution allow-list are recognised (a tail such as `: Bad file descriptor` is not, so the line stays damage as its anchored pattern reads it), and a name that merely contains an execution message in the middle (`OEBPS/ch: Permission denied/x.xhtml`) is a file name, not an execution error.
* **The `zip_crc` member suffix is read on the whole text** (`_zip_crc_readings`, W25b A37-1). Both collectors write ONE message and then ` in member <name>` (`evidence/epubtool.py`: `<Type>: <message> in member <name>`; `tools._epub_stage`: `CRC mismatch in member <name>`), so the suffix is recognised before the text is split into lines, and a line break in the name is part of the name. The name may hold colons (`a:b.xhtml`, `Part 1: Intro.xhtml`), line breaks, a leading space and ` in member ` itself; every occurrence of the separator that starts within the first 320 characters is a reading (at most 32; the collectors' message before it is at most `<Type>: ` and 200 characters), and a reading copies only that message, never the name. A separator further in gives no reading: such a text is read line by line, as under diag-1, after the complete-diagnostic check above. So `Error -5 while decompressing data: incomplete or truncated stream in member a:b.xhtml` is damage (diag-1: unclassified), and so are the real CRC lines of both collectors for names such as `a in member b.xhtml`, ` a.xhtml` and `a<newline>b.xhtml`; the live collector's `Bad CRC-32 for file '<name>'` cut at 200 characters is recognised by rebuilding it from the suffix (`_live_bad_crc`). A text whose name ends in an execution error (after `: ` or on a line of its own: `CRC mismatch in member a<newline>b.epub: Permission denied`) is an execution failure, and the execution check of each reading still comes first, so file-name and execution precedence are kept (`File is not a zip file in member book.epub: Permission denied` stays execution). Precedence goes to execution on purpose: a member whose real name ends in `: Permission denied` is read as an execution failure, never as damage that could support a write.
* **One empty spine document is not damage.** `AssertionError: a spine document has no text` (tools behaviour v2 / v3: the vendored inspector stopped at the FIRST spine document without text, which an image-only cover page also is) is unclassified under diag-2: the text does not say whether every document was empty. Tools behaviour v4's `AssertionError: the spine documents contain no text` (every spine document empty) is damage.

**Tools behaviour v4** (`tools.py`) is tools behaviour v3 with three EPUB package-check corrections; every other rule, the body excerpts and the literal media text are v3's:

* **Image-only spine documents.** When the vendored inspector stops at `assert text` (one spine document without text), `_inspect_v4` re-runs its checks in its order with its result shape, records that document with 0 characters, and fails (`the spine documents contain no text`) only when every spine document is empty. This is what the live collector has always done (`the parsed spine documents contain no text` only when the parsed documents have no text at all), so the replay and live paths agree.
* **Remote manifest hrefs.** `_epub_stage(path, remote_ok=True)` and `_inspect_v4` treat an href as a remote resource only when it is an `http` or `https` URL or has a network location (`//host/...` with any scheme; `tools.remote_href_v4`): counted as a manifest item, never resolved inside the archive, so never a missing member. Any other colon is part of a LOCAL member name (W25b, Opus 3): `Part1:Intro.xhtml` (which `urlsplit` reads as the scheme `part1`) resolves to `OEBPS/Part1:Intro.xhtml` and is read (`tools.local_href_v4`). A remote spine item is not read, as the live collector skips it, and is counted in `remote_spine_items`. A missing LOCAL member is still the `manifest` failure.
* **An all-remote spine.** A spine whose items are all remote is not `the spine is empty` (it is not): the result is ok, with `spine_items: 0`, `remote_spine_items` and `spine_note: every spine item is a remote resource: no spine document is in the archive, so no spine text was read` (`tools.ALL_REMOTE_V4`). The live collector reports such a package valid, so replay and live agree (clean). A spine that lists no item at all is still `the spine is empty` (damage; live: `the spine lists no items`).
* **What the live collector still does differently (disclosed limitations, for the #145 follow-up).** `evidence/epubtool.py` is shared by every configuration and is unchanged (no version selects a new one). Its `_resolve` reads ANY URL scheme as remote and skips the item, so:
  * **a colon-named member** (`Part1:Intro.xhtml`) is never read live. When it is the only spine document, the live collector parses nothing and reports the package valid and clean whatever the member holds, while tools v4 reads it: an EMPTY document is damage (`the spine documents contain no text`), a MALFORMED one is damage (the inspector's `ParseError`, for example `no element found: line 1, column 12`), and an ABSENT one is damage (`manifest names members that are not in the archive: ['OEBPS/Part1:Intro.xhtml']`). Only a well-formed colon-named document with text gets clean on both paths;
  * **a `data:`, `urn:` or `mailto:` manifest href** (or any other non-http scheme without a network location) is skipped live, while tools v4 resolves it as a local member that is not in the archive, so it is the `manifest` failure (damage) on v4 replay.
  Both are disclosed, not fixed: making the two paths agree needs an opt-in versioned live resolver with missing, malformed and empty regressions, a separate story. (W27: live collector behaviour `live-2` is that resolver; `live-1`, described here, is unchanged. See the next section.)
* **Size-cap wording.** `SIZE_CAP_V4` says what the inspector compares: at most 8 MiB (`<=`), fewer than 2000 members and less than 32 MiB uncompressed (both strict `<`). Tools v2 / v3 keep `SIZE_CAP_V2` ("at most ... 2000 members and 32 MiB"). Both are execution failures under diag-1 and diag-2.
* Every EPUB the vendored inspector accepts gets the vendored result unchanged under v4 (the corrected inspector runs only after the vendored one stopped at one of the two relaxed asserts).

**Effect on the public suites** (`docs/w25-deltas.json`): none. diag-2 changes the typed verdict of none of the 176 case-evidence observations of either public dev suite, and tools behaviour v4 changes none of the 17 `epub_inspect {}` results per suite. Tests: `tests/test_w25_bugfixes.py` (each regression fails at `6ca16ae0`; each control pins the earlier version).

## Diagnostic rules diag-3 and live collector behaviour live-2 (W27, OpenProject #145 remainder and the PR #1031 nits; opt-in, offline)

Two more new versions and one crash fix; nothing above changes. Every configuration the runner can select, every record and every committed result still reads `diag-1`, tools behaviour v1 to v3 and live collector behaviour `live-1` (every collector as it was). The new versions are selected programmatically (`evidence_v2.diagnostic_rules('diag-3')`; `evidence.collect(..., live_behavior='live-2')` or `tools.Context(..., live_behavior='live-2')`) by the tests and `scripts/w27_deltas.py`. No runner option selects them yet.

**diag-3** is diag-2 plus three corrections (`evidence_v2.py`); every diag-2 rule applies unchanged:

* **The cross-line `error reading header` rule reads every decorated form** (#145 item 2). The one cross-line rule (an `error reading header` warning directly followed by an execution-error line is that execution failure) recognised the header line only behind brackets (`[mov,mp4 @ 0x...] error reading header`). Under diag-3 it recognises it in every reading the line classifier strips the line to (`_header_line`, `_candidates`): `pipe:0: `, `in#0: `, a file name or path, `Error opening input: `, a bracket run. So `pipe:0: error reading header` followed by `pipe:0: Permission denied` is two execution lines, not a decoder warning. A damage or unrecognised neighbour still decides nothing.
* **An OSError at `zip_open` is an execution failure** (#145 item 3). The offline inspector (`tools._epub_stage`) and the live collector write an exception at stage `zip_open` as `<Type>: <message>`. An OSError whose message is not on the execution allow-list (`OSError: [Errno 6] No such device or address`, `[Errno 40] Too many levels of symbolic links`, `[Errno 23] Too many open files in system`) was an unclassified failure with cause `unknown`. Under diag-3 an `OSError` or any of its builtin subclasses (`OSERROR_TYPES`, a fixed list) at `zip_open` is an execution failure (`cause: tool`): the inspector could not open the file. A positive damage diagnostic in the same text still wins (damage is read first: `OSError: File is not a zip file` is damage), and every other exception type at `zip_open` (`EOFError`, `KeyError`, `NotImplementedError` ...) and every other stage keep their reading. **EINVAL is left out** (`[Errno 22] Invalid argument` stays unclassified): depending on the Python version, zipfile's own seek raises it on a DAMAGED archive (a ZIP64 end-of-central-directory locator that points before the start of the file; the Python on this pod says `BadZipFile: Corrupt zip64 end of central directory locator` instead, which is damage), so it does not show a failure to open. **Disclosed disparity (not changed):** the live EPUB collector's own `cause` calls every OSError at `zip_open` `tool` (`epubtool._cause`, every behaviour), and the typed layer keeps a live collector's cause, so a live EINVAL at `zip_open` reads `cause: tool` while the same text offline reads `cause: unknown`. Both are non-damage (integrity unknown, no known defect, no write support).
* **The `zip_crc` execution check starts at the first separator anywhere** (PR #1031 nit). Under diag-2 only ` in member ` separators that start within the first 320 characters were readings, so a text whose first separator lay further in was read line by line, and `error: Error -3 while decompressing data: invalid block type<newline><330 characters> in member a: Permission denied` was damage with write support met. Under diag-3 the first separator is found anywhere with one linear `str.find` (`_first_member_name`), and a name after it that ends in an execution error makes the text that execution failure (`_ends_in_exec`, linear). Only the list of damage readings stays bounded (320 characters, 32 readings), exactly as under diag-2, so diag-3 differs from diag-2 only for a first separator beyond 320 characters. A 65,000-character input classifies in about a millisecond (the test bound is 50 ms).
* **Several `error reading header` readings no longer depend on the hash seed** (found in the W27 review; present in diag-1 and diag-2, which stay as they are). A line such as `a.mkv: error reading header: b.mkv: error reading header: Permission denied` has two readings that disagree (one ends in an execution error, one does not), and the line classifier took the first one met in a set, so the class depended on `PYTHONHASHSEED`. diag-3 weighs every reading, execution first. No public diagnostic has such a line (the public deltas are the same under any seed the review tried).

**Live collector behaviour live-2** (`evidence/core.LIVE_BEHAVIORS`; `live-1` is the default and byte-identical; a live-2 record of a kind it changes, decode, audio, audiobook or EPUB (`LIVE2_KINDS`), says `collector_behavior: live-2`; a probe or frames record is the same as under live-1 and is not marked):

* **Damage after start-up warnings, or behind a long decoration, is kept, in no more bytes than live-1** (#145 item 4; review rounds of `f399cda0` and `8162e028`). A decode window kept only its first 3 diagnostic lines (`avtools.py`, `errors`), each cut to 160 characters plus `...` (163 characters, `_clip`), so located damage printed after start-up warnings (`non-existing PPS 0 referenced` three times, then `error while decoding MB 3 7, bytestream -5`) read as a decoder warning, and a damage line whose decoration is long (`[h264 @ 0x1] /long/<130 characters>.mkv: error while decoding ...`) lost its message to the cut; both read integrity unknown. Under live-2 (`avtools.kept_error_lines`) every line is classified WHOLE, before it is cut (with `diag-1`'s allow-list, whose damage set contains every later rule set's; the typed layer classifies the kept text again under its own rules). **The budget is bytes, not characters:** a window's list never takes more bytes in a tool result (UTF-8 with JSON escaping, what `to_tool_result` writes) than live-1's own list for the same window, and the record's `stderr` excerpt is live-1's, byte for byte, so a live-2 record never takes more bytes than the live-1 record of the same run and fits every cap live-1's fits (a 163-character form can take three times the bytes of live-1's ASCII cut when it ends in a CJK path; the `8162e028` draft let ten such windows push a record that fits 8 KiB under live-1 past the cap, where it read unknown). When one of live-1's 3 lines already shows damage, the window keeps exactly live-1's lines. Otherwise the first line that is damage whole (among the first 3, else the first later one) is shown in the most faithful form that still reads as damage and fits: the whole line or live-1's cut, its start and end with ` ... ` between them, its end after `... `, and finally the reading the classifier recognised, behind the elision mark `[...] ` (a bracket run the classifier strips as decoration: `[h264 @ 0x1] Error opening input: ... moov atom not found` is shown as `[...] moov atom not found`, which no fixed cut position keeps); it takes its own place (a later line: the third place) beside as many of live-1's other lines as fit. `error_lines` still counts every line. The audio collector's level windows (`problems`) get the same selection (their excerpt is the raw problem lines, as before). Under live-1 a window keeps its first 3 cut lines, as before.
* **The live EPUB collector resolves hrefs exactly as tools behaviour v4** (PR #1031 nit, live/replay URI parity). `epubtool._resolve_live2` gives the same answer as `tools.remote_href_v4` and `tools.local_href_v4` (a test compares them): only `http`/`https` URLs and references with a network location (`//host/...`) are remote and skipped; every other href names a LOCAL archive member. Like v4's package check, live-2 checks every manifest item with an href for a missing member, one without an id included (live-1 checks only items with an id). The two inspectors still differ in what they read beyond the hrefs (their own checks, messages and caps); the agreement claimed here is the resolution of hrefs and the verdicts in the cases below. So a colon-named sole spine document (`Part1:Intro.xhtml`) is read: EMPTY (no text) is damage (`the parsed spine documents contain no text`), MALFORMED is damage (not well-formed XML), ABSENT is damage (`manifest names 1 member(s) that are not in the archive`), as on v4 replay, and a well-formed one with text is clean on both paths.
* **`data:`, `urn:` and `mailto:` manifest hrefs are local member names, live and on v4 replay** (the decision; corrected in the review round, AUDIT-ASTRA-48). An EPUB's publication resources are archive members or remote web resources; EPUB 3 does not allow a `data:` URL in the manifest, and `urn:` and `mailto:` name no resource the package can contain. So such an href is read as a LOCAL member name (`data:text/html,hello` names `OEBPS/data:text/html,hello`). When that member is absent, which is what a real `data:`, `urn:` or `mailto:` reference means, it is the `manifest` failure, damage, on both paths (live-2 and tools v4). When the archive does hold a member with that literal name, the href resolves to it and both paths read the package as ok and clean. live-1 skips such hrefs (clean), as before.
* **The member names in the EPUB failure messages and lists are bounded in bytes** (review rounds of `f399cda0`, `8162e028` and `ffd9a029`). Under live-2 each member name the EPUB record reports in a failure (the missing members in the `manifest` error, its reason and `manifest_missing`; the OPF name; the member of a CRC failure; the spine documents that fail to parse) is cut at 200 BYTES as a tool result writes it (`_name_live2`), with `...[+N chars]`, a harness cut marker the classifier reads as no text. A manifest failure lists at most 10 names, and only as many as keep its FINAL fields, the message twice (`error`, and `reason`) with the names in Python's list form (whose escapes JSON escapes again) and `manifest_missing` once, within 2,400 bytes together (`_manifest_failure_live2`); the names left out are counted from the whole list (`(+N more)` in the message, `manifest_missing_omitted`). `parse_failed` takes at most 1,200 bytes (`parse_failed_count` counts every one). **A CRC failure is written as quoted evidence:** `BadZipFile: CRC mismatch in member "<name>"` for zipfile's `Bad CRC-32 for file '<name>'` (whose message holds the name), and `<the exception's own message> in member "<name>"` otherwise; inside the quotes the quote, the backslash, `:` and every line break or control character are written `\uXXXX`, and the name is cut at 200 bytes inside the quotes. So nothing a name holds can end the quotes, start a line or put a separator before an execution message, and the evidence reads the same under diag-1, diag-2 and diag-3 whatever the name says (round 4: a cut could add an execution tail, `'a' * 181 + ': Permission denied' + 'z' * 40 + '.xhtml'`, or remove one, `'OEBPS/' + 300 x + ': Permission denied'`, which live-1 and v4 replay read as execution by their name-suffix rule; the quoted form reads damage, the CRC failure it is). A missing `data:` href of 5 KB (at the 8 KiB cap) or 400 KB (at the 1 MiB cap), five missing hrefs of 250 CJK characters, twenty with `%7F` runs beside a 1,004-character OPF name, or a CRC failure in a 10,000-character member name each pushed the record past the cap and lost the failed stage (unknown live); now all read damaged. Names elsewhere in the record (titles, metadata) are not bounded here, as under live-1, and a non-CRC exception message that itself quotes a name (zipfile's `File name in directory ... and header ... differ`) is kept as zipfile wrote it.

**Pagination (crash fix, `pages-v1` unchanged).** A list that mixed strings and dicts raised `AttributeError` once a dict element had to be divided to fit a page (`_split_further` indexes the dict elements; the lookup of an index then met a string). `_descend` and `_put` now look an index up among dict elements only. The fix changes only inputs that raised: every list that paged before pages to the same bytes and cursors (a test pins three page sets computed with the 9702fa29 module), so it is not a new contract version. A plain element keeps no index (as before); the divided dict keeps its position as `_i`. In such a list `<field>_shown` counts the plain elements only, which is what it already meant for any list once its dict elements were indexed.
