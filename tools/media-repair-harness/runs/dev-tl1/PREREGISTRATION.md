## 1. Purpose and hypothesis, in plain words

**The question.** Today the harness hands a local model the evidence it needs: the output of `ffprobe`, `decode_sample`, `arr_lookup` and the like is collected beforehand and sits in the first message. #207 found that, with that evidence already in front of it, a local model seldom calls a tool (qwen3.8:27b called `ffprobe` in 2 of 180 offering cases and `arr_lookup` in 30 of 248). So the existing results say how well a local model reasons over evidence someone else gathered. They do not say whether it would gather the evidence itself.

**The measurement.** Run the same 73 cases twice per model. In the **handed** arm nothing changes (`--evidence-handover full`, today's behaviour). In the **must-ask** arm (`--evidence-handover askable`, #209) the evidence that an offered tool can return is withheld from the first message. The model still sees what the item is, what was reported, which tools it may call and the 6-call budget, and must call the tools to get the evidence. A call that asks for a withheld item returns exactly the text the handed arm showed. Evidence that no offered tool can return (`prior_record` notes, an unoffered tool, an injected failure) stays in the message, so it does not test tool use.

**Hypothesis, as a plain statement (not a target).** When nothing is handed to them, these local models call some of the tools they need but not all, and reach the handed arm's decisions less often. The expected shape, from #207, is a clear drop in correctness on the cases that differ, concentrated where the evidence needs an argument (`ocr` at a time, `decode_sample` full) or several calls. The alternative the run can show is that the models ask for nearly everything and decide about as well. Either result is reported as it is.

**What it feeds.** Tom wants to know whether a local model could scan a whole TV series (the Pokémon wrong-episode case) where nothing is ever handed over: every episode's evidence would have to be fetched by the model's own tool calls. This run answers a smaller question first: when evidence is not handed over, do these models ask for it, and do they reach the same decisions? It cannot show that a model can scan a series, and the report says so (section 9): the suite's cases are single items, each with a 6-call budget and replayed recordings, and no case asks the model to choose which of many files to open.

**How the hashes were built (offline, no call).** `scripts/devtl1_config.py` runs the runner's own `main()` on each command with every adapter's `preflight` replaced by a stub that raises before anything is contacted. `main()` therefore applies its real option checks (`check_option_combination`, `check_handover_options`, the llamacpp and context-policy refusals), builds the adapter and the config, and writes `manifest.json` with the `config_hash` (`config_hash` = sha256 of `json.dumps(config, sort_keys=True, separators=(',', ':'), ensure_ascii=False)`). **All four commands are accepted, `askable` included, with every flag above.** `python3 scripts/devtl1_config.py --check` compares them with `manifest-template.json`; `tests/test_devtl1.py` pins them, and shows that:
* handed and must-ask of one model differ in the config only by the `evidence_handover` key (`{"mode":"askable","serve":"recorded-first","version":"handover-1"}`), and the handed configs have no such key;
* qwen and muse differ only in `adapter_config`;
* the handed qwen config equals the config recorded by the dev-c7-qwen-r2 run (`runs/dev-c7-qwen-r2/devc7r2-qwen3.8-27b/manifest.json`) in every key but `harness_version` (`dev-c7` there, `dev-c8` here) and `limits.max_wall_s` (2700 there, 3600 here).
A recorded `config_hash` that differs is a deviation and is reported.

**What the config does not record (named).** The `llamacpp` config holds the adapter version, the alias, the sampling options (`temperature 0`, `seed 42`, `max_tokens 640`, `cache_prompt false`), the stop list (`<|eot|>`, the harness's default for a `muse` model) and the schema variant. It does **not** hold the server's context size, slot count, reasoning setting or build, so `config_hash` cannot tell a mis-set server from a correct one. That is what the `/props` block of section 4 and the pre-run checks of section 5 are for.

**Wall cap 3600 s per run** (`--max-wall-s 3600`, one absolute deadline from just before the adapter preflight; no case or call starts unless its 120 s timeout plus the adapter's cleanup reserve fits before it; an overrun is a `wall_cap_exceeded` limit violation, exit 3, never success). dev-c7-qwen-r2's handed pass took 388 s of its 2700 s cap; the must-ask arm adds tool turns (at most 18 model calls per case), so the cap is raised for both arms and both models alike rather than set per arm. A run that hits it is PARTIAL and is not rerun (section 6). The muse runs have no measured speed yet; the cap is the same.

## 6. Retry, repair, abort and rerun rules

* **Repair:** a reply that is not one valid JSON object, or fails the frozen decision-v3 validator, gets exactly one generic repair prompt; if the repaired reply is also invalid the decision is forced to `insufficient_evidence` / `escalate` (no target) and recorded `forced`.
* **No whole-case rerun.** A failed model call is recorded with its receipt, the case ends as a forced escalate, and the run moves on.
* **Rerun on contention (Prime; owner ruling 2026-10-26, which deliberately differs from dev-c7's "no rerun of any run").** If a qwen run is **aborted by the runner's GPU checks**, it may be **rerun from scratch up to 2 times**, with the same registered command and the run id suffixed `-r2`, then `-r3`; every aborted attempt's directory and manifest are kept and reported. The checks that count:
  * the preflight's `GPU busy: model(s) ... resident` and `GPU has an existing compute owner`;
  * the warm-up GPU-fit skip (`aborted: gpu_fit_skip (full-gpu-v2)`);
  * a reload that is not 100% GPU (`aborted: gpu_fit_abort (full-gpu-v2)`).
  
  A rerun is not a new measurement: its records replace nothing and the first attempt that completed all 73 cases is the run; if none completes, the run is reported as aborted.
* **Everything else is a record, not a rerun:** a digest mismatch, a load failure or timeout, an unreadable `/api/ps` or a replaced Ollama pod (as dev-c7 was), a PSI/restart guard trip, the wall cap, an adapter error class the harness already records (transport failure, call timeout, a server `error` body, a context overflow), a leak-guard refusal, a failed or aborted llama-server preflight on a case. They stay in the tables with their counts and are not repeated. If one of them stops a run, the coordinator is told; a rerun then needs the owner's decision, not this registration.
* **muse:** the llamacpp adapter has no GPU check. A pre-case preflight failure that is not a settings mismatch (the server unreachable or not yet ready after the swap) may be retried once the server is ready, up to the same 2 reruns and with the same `-r2`, `-r3` suffixes, the attempt kept. A mismatch with section 4 is never "run anyway".
* **Started-aborted and never-started, never silent:** every planned case ends in exactly one of `records_written`, `started_aborted` (kept under `started-aborted/`, not scored) and `never_started`; each gate keeps score.py's own denominator and G7 is over the 73 planned cases; a partial run is labelled PARTIAL in every table.
* **Cost:** the local GPUs only. **No API spend, and the frontier models (Haiku, Astra) are not run.** `--no-spend-limit` is only the label dev-c7 used; both adapters report no cost.
* **Wall cap:** `--max-wall-s 3600` per run (section 3).

## 7. Outcomes, defined before any result

Scoring uses the unchanged `score.py` through `score_compat` (`python3 -m media_repair_harness.score_compat <dir> --suite $SUITE`); restored original decisions come from `python3 -m media_repair_harness.guard_cli <run> --restore --suite $SUITE --out <run>-restored` and are scored the same way ("guards off" means restored decisions from the same completions, not an independent run). **A case is correct when its `cases[<id>].correct` in `score.json` is true.** The as-recorded (guarded) view and the restored view are both reported; the primary comparison is stated on the as-recorded view and repeated on the restored view, and if the two disagree in direction the report says so. The guards read only what the model was shown or asked for (#209), so in the must-ask arm a model that skips a check can be escalated by a guard: that is part of the as-recorded view and is shown separately (table 5). Every number carries its numerator and denominator.

**Primary comparison (per model): must-ask against handed correctness on the 62 cases that differ** (the 73 minus the 11 identical-input cases of section 2; the list is `manifest-template.json`, `handover`). Reported as correct / 62 in each arm, and as the paired split (correct in both, only handed, only must-ask, neither). **Secondary: the same on the 9 identity_mismatch cases that differ** (`audiobook-identity-002`, `epub-identity-003`, `epub-identity-004`, `epub-identity-005`, `epub-insuff-002`, `movie-identity-002`, `tv-identity-002`, `tv-identity-003`, `tv-identity-004`), with all 14 identity_mismatch cases beside it. No other cut, ranking, subset or threshold is added after the results.

Tables, per model and arm unless stated (every number labelled dev-tuned):
1. **Run:** run id, `config_hash` (and whether it equals section 3), harness commit and `src` tree sha1, runtime version (Ollama version; llama.cpp `build_info`), the muse `/props` block and its equality with section 4, the qwen model digest, cases recorded of 73, started-aborted and never-started ids, aborted reason, wall time, the time of the first measured response, and for qwen the GPU-fit outcome at the warm-up and at every detected reload.
2. **Gates G1 to G10 and per-class correctness:** score.py's gates with their own numerators and denominators, and correct / n for each class (corrupt_file, decoder_incompatible, **identity_mismatch (highlighted)**, metadata_naming, order_edition_ambiguity, healthy; the insufficient_evidence abstention share), classes below 2/3 named; as recorded and restored. For the qwen handed arm the dev-c7-qwen-r2 run is shown as a reference column (not a baseline: section 8).
3. **Primary and secondary comparison**, as defined above, per model, with the paired splits and per-class counts over the 62.
4. **Calls per case (self-initiated).** Every entry of a record's `tool_calls` is a call the model asked for (the harness never calls a tool itself). Reported: total calls, calls excluding page fetches, cases with at least one call (of 73 and of the 62), the distribution of calls per case (0, 1, 2, 3, 4, 5, 6), calls by tool and their result statuses, requests for a tool the case did not offer (answered `unavailable`), and in the handed arm the calls whose tool's output was already in the first message (`evidence_shown` joined to the case's evidence, as in `docs/tool-usage-report.md`).
5. **Withheld entries (must-ask arms only, from the records' `evidence_handover`):** of the 162 withheld entries in the 62 cases, how many were **obtained by a call** (`obtained_by_call`) and how many were **never asked for** (`never_asked_for`), by tool, split into the 144 reachable by a bare call and the 18 that need an argument (`decode_sample` full, `ocr` at a time); cases that asked for all, some or none of their withheld entries; the correctness of each of those three groups (descriptive only); the guard-made escalations of each arm (case, rule, original and final decision; as dev-c7 table 5).
6. **Control: the 11 identical-input cases.** Both arms receive the same first message and tools but the model-visible case alias (section 8); the table counts the cases whose decision (class and action) is equal in the two arms and those that differ. It is the measured noise of this design, shown next to table 3.
7. **Validity and failures:** forced decisions, first-attempt-valid, repaired and forced replies, protocol violations, repair prompts by failure mode, adapter errors by class, leak-guard refusals, context flags (qwen: the dev-c7 reported-count flags; muse: the adapter's context record against `n_ctx` 16384), limit violations.
8. **Flips:** every case whose correctness differs between the arms of one model, with its class, its two decisions, its withheld entries and which were obtained or never asked for, and the **attribution** below.

**Attribution of a flip from correct (handed) to incorrect (must-ask), registered:**
* **A. did not ask:** at least one withheld entry was never asked for;
* **B. asked everything it could and still differed:** every askable entry was obtained and the decision differs, so the cause is reasoning over what it got (including the order and the 6-call budget), not tool use;
* **C. unreachable entry:** the case keeps an entry no tool can return (`movie-decoder-001`, `tv-insuff-001`, `tv-insuff-002`) and the attribution is not separable.
A case gets one label by that order; the counts per label are reported with the denominator "cases correct in handed and incorrect in must-ask". Anything read from a transcript by hand (a model's own `reason` naming a missing capability) is labelled **hand reading** and never counted in a table.

## 8. Confounds and limits, named (none can be separated by this design)

* **The prompt is not adapted to the must-ask arm.** Prompt v7 says "using ONLY the evidence you are given and the read-only tools you call" and lists the tools' arguments, and is the same text in both arms. A model told outright that nothing is attached might ask more. This measures the prompt as it is.
* **Qwen runtime and code.** Ollama 0.40.11 now against 0.40.6 / 0.40.7 in every earlier qwen record; `HARNESS_VERSION` `dev-c8` against dev-c7 (opt-in changes only; the handed config equals dev-c7-qwen-r2's but for the version and the wall cap, section 3); the wall cap 3600 against 2700. The dev-c7-qwen-r2 numbers are a reference for the handed arm, not a baseline.
* **muse is new at this configuration:** prompt v7 / format v3.1-format has never run on it, and its earlier record (dev-c4, `muse-glimmer:30b` on Ollama, prompt v4) is not comparable. The runtime is llama.cpp b11096 with benchmark settings, `--cache-type-k/v q8_0` and flash attention as in voice, and its own tokenizer and context accounting: the dev-c7 page budget (8192 bytes) was sized for qwen's counts at 16384 tokens; an overlong prompt is a server error recorded as an adapter error (`llama-server` rejects rather than cuts).
* **The model-visible case alias** is derived from the run id (`leakguard.alias`, an HMAC of the run id and the case id), so the same case carries a different alias in each of the four runs and in every rerun. It is the only text that differs between the two arms of the 11 identical-input cases (table 6); it differed between earlier qwen runs too.
* **Between-arm drift:** if the Ollama image or the llama-server pod changes between a model's two arms, the pair is not like-for-like and the report says so.
* **muse stop string:** `<|eot|>` is the harness default for a `muse` model from the Ollama days; the smoke records the chat-template hash but nothing registered tests that this is muse-glimmer's end token. It cannot change a record's validity (a stop string that never appears does nothing).
* **Dev suite, one sample.** Correlated, previously tuned fixtures; a difference of a few cases is within the noise table 6 measures. No significance test, no confidence interval and no readiness claim is made or implied.
* **The guards v3 shape the as-recorded view;** hence the restored view beside it.
* **Replay evidence:** a call returns a recording, never a live probe; no case needs a file the model must choose among.

## 9. What will be reported to the owner, and the decision it feeds

After the runs (offline, no model call): `runs/dev-tl1/README.md`, written once, with tables 1 to 8 and these statements verbatim: dev-tuned; one pass per model and arm on correlated, previously tuned fixtures, neither significance nor generalisation; no readiness claim; the arms differ only in what is handed (the prompt, tools, budget and guards are the same code), and the 11 identical-input cases show the noise; frontier models were not run; G6 measures fixture verification, not completed repairs.

The written answer for Tom (to OpenProject #208 and to the coordinator) has three parts, each with counts and denominators:
1. **Do local models gather evidence themselves?** For each model: how many of the 162 withheld entries were obtained by a call and how many were never asked for, the cases that asked for all, some or none, and how the decisions on the 62 cases changed against handed (primary) and on the 9 identity cases (secondary), read against the control.
2. **Is the current toolset enough for a series scan, or which gaps show?** The report states what the data bears on and what it cannot: it measures asking, not scanning. It lists (a) requests the toolset could not answer (`unavailable`, unoffered tools), (b) the entries the toolset cannot return at all (the 14 kept in the first message: 13 `prior_record` notes and 1 injected failure, so not tested here), (c) flips of attribution A (a failure to ask, a prompt or driver question) against B (a reasoning failure after asking) against C, (d) the 6-call budget against what a series needs: calls per case times the number of files is shown as arithmetic, labelled as such. **No pass line is registered:** this registration invents no threshold at which "enough" is declared; the counts go to Tom, who decides.
3. **What this does not show:** a model scanning a series, choosing among files, or working live rather than from recordings; the suite has no such case.

The decision it feeds (Tom's, not this registration's): whether to let a local model scan a series with the current tools, build the evidence-collecting driver around it (the harness collects, the model judges, as in the handed arm), or add tools first.
