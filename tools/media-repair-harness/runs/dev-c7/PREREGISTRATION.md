## 2. Context policy (frozen)

**qwen runs at `num_ctx 16384`** through the new versioned, opt-in `--context-policy ctx16k-v1` (`adapters.CONTEXT_POLICIES`): it is the only way to send a `num_ctx` outside 4096 / 8192, it requires `--num-ctx 16384`, and it is recorded in the adapter config (so in the config hash). `num_predict` stays 640 (the output reserve), so the **input budget is 16384 - 640 = 15744 tokens**.

**Page budget: the registered default, `--tool-output-bytes 8192`, on all three runs** (not 4096). Reasons, sized offline with `scripts/devc7_context.py` (output `runs/dev-c7/context-sizing.json`; it reuses `devc7_sizes.py`'s sequences and estimate rule):
1. **It fits 16384.** 383 scripted conversations per budget with maximal replies (the first message alone; the 219 tool-call sequences the three dev-c6 runs made, re-run under v7 + v3.1-format with every page fetched; the first six advertised operations of `passability-1` with every page fetched; and, for the 9 readable EPUBs, `{}` then five maximal excerpts, and `{}` plus one excerpt with every page fetched). At 8192 the largest pessimistic estimate (characters / 3 + the 640 reserve) is **15,970 < 16,384**, so no prompt estimate reaches the 15,744 input budget (largest prompt estimate 15,330); 0 of 383 reach 16,384. Divided by 3.97 characters per token instead (the LOWEST ratio of prompt characters to reported `prompt_eval_count` over the 107 dev-c6 qwen turns, median 4.27), the largest is 12,224 including the reserve. At 4096 the figures are 14,833 and 11,365. (A calibration on v6 + format v3 text; EPUB body text is new, so it does not certify v7.)
2. **It keeps every first message on one page.** At 8192, 0 of 73 first messages are paginated; at 4096, 28 of 73 are (up to 3 pages), and each extra page costs one of the 6 calls. 4096 would change what every model is shown on 28 cases and what a passability witness costs.
3. **It removes a confound.** dev-c6 ran all three models at 8192, and all three dev-c7 runs use the same budget, so the page budget differs neither from dev-c6 nor between the dev-c7 models. W22's "least-tailored" 4096 candidate was chosen for an 8192 context, where v7 cannot fit at any budget; at 16384 that reason no longer applies.

**Truncation flags (per turn, from Ollama's REPORTED counts; recorded by the adapter, `meta.context`, and summarised per case in `context_check`):**
* `prompt_reaches_input_budget`: reported `prompt_eval_count >= 15744` (16384 minus the output reserve). This is the work order's flag.
* `reported_prompt_did_not_grow` (case level, turn indices in `prompt_did_not_grow_turns`): a later turn whose reported `prompt_eval_count` is not above the previous turn's reported `prompt_eval_count + eval_count`. A later request carries the whole earlier request, its reply and at least one new message, so a count that did not grow means Ollama dropped content; Ollama drops whole old messages when a chat prompt exceeds `num_ctx`, which can leave the reported count below the limit, where the first flag cannot see it. Checked on recorded data: across the 87 consecutive-turn pairs of the dev-c6 and dev-c5 qwen runs (no truncation there) the smallest growth beyond prompt + reply is +39 tokens, and the rule fires 0 times.
* The earlier reported-count flags stay (`prompt_at_context_limit`: `>= num_ctx - 8`; `context_full_after_generation`: prompt + output `>= num_ctx`).
* Secondary, not evidence of truncation: `estimated_prompt_exceeds_context` (characters / 3 `>= 16384`).
Ollama 0.40.6 reports the FULL prompt in `prompt_eval_count`, cached tokens included: in dev-c6 the characters-per-reported-token ratio is the same on first turns (median 4.32) and later turns (4.18, 4.12) while later turns' prompt-eval time halves, so the count is usable as the primary flag.

**Reporting (registered):** a case with any reported-count flag is **possibly truncated**; a case with only the estimate flag is **estimate only**. All recorded cases are scored as recorded, and TWO subset rows are added to every qwen table (offline `score.py --only` rescores, labelled as subsets, never as the whole suite): **(a)** cases with no reported-count flag; **(b)** cases with neither a reported-count flag nor the estimate flag. Nothing is rerun. For every flagged qwen turn the report gives the reported and estimated prompt tokens and their ratio. **Registered expectation** from the sizing: no estimate flag and no reported-count flag; the subsets then equal the whole set, and the report says so. The same rows are not computed for the hosted models (no local context limit applies).

## 3. GPU safety (qwen only; mandatory)

**Offline GPU-fit check (made, no Ollama call): expected to fit fully on the GPU.** `scripts/devc7_gpu_fit.py` (output `runs/dev-c7/gpu-fit-offline.json`) reads only what dev-c6 recorded (`runs/dev-c6/devc6-qwen3.8-27b/manifest.json`): the `/api/tags` metadata of `qwen3.8:27b` (family `qwen35`, 27.3B, Q4_K_M, embedding 5120, trained context 262144, blob 17,741,872,154 bytes = 16,920 MiB, digest `aaee06c3...7097813`) and the nvidia-smi snapshot before the load (1 MiB used, **24,124 MiB free**). The recorded metadata carries no block, head or head-size counts, so the KV cache is computed under a STATED assumption, the published Qwen3.5 hybrid layout of family `qwen35` (64 blocks, full attention every 4th: 16 attention blocks x 4 KV heads x 256, f16; 48 Gated DeltaNet blocks with a fixed state), with one parallel slot and f16 KV (the `ollama-prime` HelmRelease sets neither `OLLAMA_NUM_PARALLEL` nor `OLLAMA_KV_CACHE_TYPE`). Weights 16,920 + KV at 16384 1,024 + linear-attention state 150 + compute-graph allowance 1,536 + CUDA-context allowance 512 = **20,142 MiB, about 3,982 MiB below the free memory**. Under a conservative bound that gives all 64 blocks full-attention KV (4,096 MiB), **23,214 MiB, about 910 MiB below**. The dev-c6 run at 8192 generated at 65.3 tokens/s median (minimum 50.9 over 107 turns), a rate consistent with every weight read from VRAM; dev-c6 recorded no `/api/ps` after its load, so this is an inference. The allowances are not derived, Ollama decides the GPU/CPU split itself at load time, and the layout is assumed: **this estimate never authorises a run; the runtime check does.**

**Runtime check at warm-up (decisive): `--gpu-fit-check full-gpu-v1`** (new, versioned, opt-in; recorded in the adapter config). Right after the registered warm-up, the adapter reads `/api/ps` once. Full GPU means the model this run loaded is the ONLY resident, `size_vram == size` (Ollama's own "100% GPU"), and a reported context length, when the server reports one, is not below 16384. Anything else (any CPU share, an unreadable `/api/ps`, missing fields, another resident) is a **GPU-fit skip**: the run unloads the model it loaded (`keep_alive: 0`), runs no case (exit 3, `aborted: gpu_fit_skip (full-gpu-v1): <reason>`, the reading in `manifest.preflight.gpu_fit`), and the qwen run is **skipped and recorded, never run partly on the CPU and never retried** (no lower context, no second load). Haiku and Astra still run.

**Wall cap 2700 s** (`--max-wall-s 2700`): ONE absolute deadline from just before the adapter preflight (load, warm-up, the GPU-fit read, every call and the checks inside it); no case or call starts unless its 120 s timeout PLUS the fixed 180 s cleanup reserve fits before the deadline, so the cleanup fits inside 2700 s; an overrun is a `wall_cap_exceeded` limit violation (exit 3), never success. dev-c6's pass took 303 s.

**Ollama Prime rules (unchanged):** `declare-activity start "dev-c7 qwen pass" --scope ai,ollama-prime --ttl 60m` before the run and `declare-activity end <id>` after; `/api/ps` must be EMPTY first: if any model is resident that this run did not load, the run is SKIPPED (the runner aborts before loading; no wait, no retry); a digest mismatch also SKIPS it (`--require-digest`; nothing is loaded); a load failure or timeout ABORTS with no retry and no replay (the half-loaded model is not unloaded or reused). `use_mmap false`, temperature 0, seed 42, `think false`, `keep_alive 2m`, load (warm-up) timeout 900 s, call timeout 120 s, one resident model, serial, the PSI/restart guard on (a trip aborts cleanly), unload only what this run loaded, no pulls, no global settings change. A skipped or aborted qwen run does not stop the Haiku and Astra runs.

## 5. Retry, repair, timeout and abort rules (the harness defaults, frozen; as dev-c6)

* **Repair:** a reply that is not one valid JSON object, or fails the strict validator (for a decision: the frozen decision-v3 validator), gets exactly ONE generic repair prompt. If the repaired reply is also invalid the decision is FORCED to `insufficient_evidence` / `escalate` (no target) and recorded `forced`. First-attempt validity is never repaired after the fact.
* **No whole-case rerun, ever, and no rerun of any run.** A failed model call (CLI error or timeout, a Codex call with no agent message or a plan or rate limit, an Ollama transport error or call timeout) is recorded with its receipt, the case ends as a forced escalate, and the run moves on. A run whose calls fail repeatedly (a plan quota wall, for example) is reported as it is, with the adapter-error count next to every table; it is not repeated.
* **A leak-guard refusal** (`leakguard-media-2`, including its disclosed false refusal of prose that spells a protected value) is a harness error of that case, kept in every denominator, never retried.
* **Before the first case only:** a failure that is not a model result and happens before any case starts (a CLI not found, a preflight error) leaves its directory in place; for Haiku or Astra the run may be started ONCE more with the same registered command under the run id with suffix `-r2`, and both attempts are reported. For qwen a busy Ollama, a digest mismatch or a GPU-fit skip skips, and a load failure aborts (section 3); none is repeated.
* **Aborts** (the run stops, exit 3, reason in the manifest): the qwen skip and abort conditions above, the PSI/restart guard trip and the qwen wall cap. Haiku and Astra have no cap and no abort beyond a preflight failure.
* **Started-aborted and never-started, never silent.** Every planned case ends in exactly one of `records_written`, `started_aborted` (persisted in `started-aborted/<case>.json` with every turn, tool call, usage figure and the abort reason) and `never_started`. **Started-aborted cases are NOT scored; they are listed unscored.** The unchanged scorer reads only `<case>.json` records, so they appear in its `missing` list and G9 crash list. **Each gate keeps score.py's own denominator; G7 is measured over the 73 planned cases.** Recorded, started-aborted and never-started counts are reported next to every gate, and a partial run is labelled PARTIAL in every table.
* **Hosted models:** the response model id of every record is checked against the request; any difference is reported in the run table.

## 8. Benchmark-passability report (Astra; policy `passability-2`; neutral evidence for the evaluator; no label change is proposed)

Computed by `scripts/passability_v2.py` (sha256 in section 1) from the copied Astra records, their restored copies, the suite, the unchanged score.py's per-case facts and the frozen rubric v3.1 checker. **Why a new version:** `passability-1` reads a run as format v3 / tools behaviour v2 presented it; a v3.1-format run differs, and reading it with v1 would misattribute: v1 would give the legacy spine heads to the checker as content (v3.1 withholds them, D32-3), read an explicit excerpt as a package check, serve exploration candidates with tools v2, count pages with the v3 session at a fixed 8192 bytes, and render fidelity's source with the v3 renderer. **`passability-2` = `passability-1` with exactly five changes**, installed into an independent instance of the frozen script (the v1 module is never modified):
1. the case evidence is resolved as the v3.1 run resolved it (tools behaviour v3 context; EPUB evidence literal with only locators aliased);
2. the checker reads the observations typed as the v3.1 audit types them (`evidence_v31.internal`: an explicit excerpt is a reading; `without_legacy_heads`);
3. exploration candidates are served by tools behaviour v3 (a recorded case-evidence epub_inspect result without body text does not make `epub_inspect {}` "already shown", since that call returns body text the recorded one lacks), links are computed over the v3.1 analysis, and a witness's page cost is counted by the real v3.1-format session at the run's `wire_bytes`;
4. fidelity's source rendering is the v3.1-format renderer, read back by the same parser (`facts.facts_from_body`) that reads the delivered transcript;
5. free-text identity: once EPUB body text is among the observations, an `identity_disagreement` row (D-ID-1, A-BLK-4) that the checker reports `unmet` (it reads no body text, C32-4, and no longer sees the heads) is reported `unknown`, as passability-1 reported free-text identity; it never becomes `met`.
Rows, columns, categories (in order: non-model failure, guard change, score-correct write with unmet or unknown prerequisites, model error, not obtained (unfetched page), presentation problem, obtainable not obtained, undetermined (hand judgement), evidence gap), the exploration constants (6 calls with pages, 5,000 evaluations, 3 rounds), the fidelity rule, the independent tension annotation and the rule that the script makes no hand judgement are those of dev-c6 section 6 as amended, unchanged. Coverage limits: those of `passability-1`, plus: explicit EPUB excerpts are not explored (the checker reads none, so an excerpt cannot meet a prerequisite).
**Evidence that the adaptation changes nothing it should not (tests/test_passability_v2.py):** every category is reachable under v3.1-format; each change has its own test; and a scripted, no-model C7 run that replays the dev-c6 Astra run's recorded tool calls and model decisions under v7 + v3.1-format gets, row by row, the 31 categories passability-1 gave dev-c6 (the EPUB rows' exploration now serves the tools-v3 `epub_inspect {}`). Hand judgements made afterwards are recorded with their reason and marked, beside the computed category, which is never overwritten. The section ends with the count per category, the dev-c6 to dev-c7 transition (table 11) and the cross-reference: which of the 6 tension cases Astra got right and which wrong.

## 9. Confounds, named (none can be separated by this design)

* **`num_ctx 16384` against dev-c6's 8192 (qwen only).** It changes the KV allocation and the truncation risk (dev-c6 had no reported-count flag at 8192 and 4 estimate-only cases); with temperature 0 and seed 42, a different context size can still change numerics and so outputs. Hosted models have no `num_ctx`.
* **Prompt v7 against v6** (+3,153 bytes; seven targeted changes: the typed completion rule with the 1 s tolerance, the empty container tag map, the EPUB body view and excerpt arguments, declarations / content / reports, the `available_check` sentence, legacy heads `legacy_mixed`, navigation excluded from body text).
* **Format v3.1-format and tools behaviour v3 against v3 / v2:** EPUB body index, default excerpts and explicit excerpt calls, statement kinds, prior-record typing, the legacy heads withheld from the audit's checker, `leakguard-media-2` (whose refusal is a harness error).
* **Audit typing:** audit v3 under v3.1-format reads an excerpt as a reading and withholds the legacy heads, so table 12 and the passability rows on EPUB cases are not like-for-like with dev-c6.
* **`passability-2` against `passability-1`** for the Astra report (section 8).
* **Harness code:** W22's dev-c7 changes and this story's measurement flags (no behaviour change without the flags).
* **Hosted serving and runtime versions:** the same model ids, but hosted models carry no digest and can be served differently on another day; Claude Code 2.1.299 and codex-cli 0.162.1 at registration; the versions recorded at run time are reported, and a change is named.
* **Ollama server version:** 0.40.6 at dev-c6 and in the `ollama-prime` HelmRelease at registration; the runtime version is recorded at preflight and a difference is named.
* **Day and plan state:** a quota wall shows as adapter errors, reported, never rerun.
* **Same:** suite, cases, case order, scorer, gates, guards v3, the page budget (8192), the tool budget, the model ids and the qwen digest.
