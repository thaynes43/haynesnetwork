## 2. Runs (one sample each; no iteration of v5 after a measured run; no smoke run before them)

There is no smoke run. **The warm-up inference of the Ollama adapter is registered as a pre-measurement model call**: `/api/generate`, prompt `Reply with OK`, the frozen options with `num_predict 256`, `keep_alive 2m`, timeout 900 s; its receipt (wall, load duration, error) is the manifest's `preflight.warmup`; it carries no case, is never scored, and happens once, inside the wall deadline. Haiku has no warm-up. The first model response to a CASE is the first case of each run.
A failure that is not a model result and happens before any case starts (Claude CLI not found, a busy Ollama, a digest mismatch) leaves its directory in place; a busy Ollama or a digest mismatch SKIPS the qwen pass (reported, no wait, no retry); a model LOAD failure or timeout ABORTS the pass with no retry and no replay (the half-loaded model is not unloaded or reused). A Claude infrastructure failure before the first case may be repeated once with the same frozen configuration under a new run id; that attempt is reported.
Checks that call no model (`claude --version`, `/api/ps`, `/api/tags`, `git`, offline tests) are allowed.

## 3. Retry, repair, timeout and abort rules (the harness defaults, frozen)

* **Repair:** a reply that is not one valid JSON object, or fails the strict validator, gets exactly ONE generic repair prompt (the validator error plus a fixed hint per failure mode). If the repaired reply is also invalid the decision is FORCED to `insufficient_evidence` / `escalate` and recorded `forced`. First-attempt validity is never repaired after the fact.
* **No whole-case rerun, ever. A failed model call** (CLI error, 240 s Claude timeout, Ollama transport error or 120 s call timeout) is recorded with its receipt (tokens and cost, when the failure reports them), the case ends as a forced escalate, and the run moves on. **Exceptions, with the Haiku cost cap set (the only run that has one):** a failed call that reports no cost (a Claude timeout, a non-JSON failure) stops the run after that case, flagged `cost_unreported`; and the Claude CLI stopping a call at its lowered per-call budget is a cost-cap abort (the case is started-aborted, never a scored forced escalate). The Ollama run has no cost cap, so there a failed call only ends its case. Tool calls over the budget, tools not offered and repeated calls are recorded violations and answered `unavailable`.
* **Aborts** (the run stops): GPU busy or foreign resident model, model not installed (no pulls), a digest mismatch, load failure or timeout (not retried), PSI/restart guard trip, the two caps above. Exit status 3 and the reason are in the manifest.
* **Started-aborted and never-started, never silent.** Every planned case ends in exactly one of three lists in the manifest and the run summary: `records_written` (a scored record), `started_aborted` (the model was shown the case and the abort cut it short) and `never_started`. A started-aborted case is persisted in `started-aborted/<case>.json` with every turn, tool call, usage figure and the abort reason (its cost is in the run's cost). **Scoring treatment, registered: started-aborted cases are NOT scored; they are listed unscored.** The unchanged scorer reads only `<case>.json` records, so they appear in its `missing` list and G9 crash list. **Each gate keeps score.py's own denominator; G7 uses planned cases.** Recorded, started-aborted and never-started counts are reported next to every gate, and a partial run is labelled PARTIAL in every table.
* **Context overflow (qwen, 8192 tokens):** Ollama truncates an over-long prompt silently and nothing is done to prevent it (`num_ctx` is fixed at 8192; the system prompt, the cases and the page budget are frozen). Each turn is flagged by the adapter from the REPORTED token counts (`prompt_at_context_limit`, `context_full_after_generation`) and, separately, by the 3-characters-per-token ESTIMATE (`estimated_prompt_exceeds_context`, pessimistic and not evidence of truncation).
  The report states the number of turns and cases with a reported-count flag next to every qwen table, scores all recorded cases as recorded, and adds TWO subset rows (offline `score.py --only` rescores, labelled as subsets): (a) cases with no reported-count flag, and (b) cases with neither a reported-count flag nor the adapter's estimate flag. Cases the 3-characters-per-token ESTIMATE flags but the reported counts do not are labelled **possibly truncated** in the report. Expectation, registered now: per the Opus review the estimate flags 29 of the 73 cases, so subset (b) holds at most 44 cases and may be smaller; it is reported with its size and never presented as the whole suite. Nothing is rerun. Offline, before the freeze: the v5 system prompt plus the largest first message of either public dev suite is below the 8192-token estimate (a test in `tests/test_v5.py`); a case with several large tool replies can still pass it.
* **Hosted models:** the response model id of every record is checked against the request; any difference is reported in the table.

## 4. After the runs (offline, no model call)

"Guards off" is called **restored original decisions from the same completions (not an independent run)**: `mrh-guard <run> --restore --suite <suite> --out <copy>` (the run is untouched), scored with the same unchanged scorer. dev-c4 columns are the evaluator's Sections 2 (guarded, guards v2) and 2b (restored original decisions) of the REPORT named above.

## 5. The tables that will be reported, exactly (per model run; the same layout for both; every number labelled dev-tuned)

1. **Run table:** run id, config_hash, harness commit, prompt sha256, response model ids, runtime version, digest, cases recorded of 73, started-aborted (ids, usage, reason), never-started (ids), aborted, cost and tokens as reported (Haiku), wall time (qwen, warm-up reported separately), crashes, adapter errors, forced decisions.
2. **Gates G1 to G10, guarded against guarded:** B as recorded (guards v3) next to dev-c4 as recorded (guards v2, legacy evidence, prompt v4), with threshold, PASS/FAIL, and the numerator and denominator of G2, G3, G4, G5, G6, G7, G8 and G10 (G10: records passing score.py's G10 checks / records written; each record needs a model digest or a not-applicable reason, and a response model id, plus runtime version, harness commit, config hash, fixture hashes and raw requests and responses; G7 also as first-attempt valid, repaired and forced counts).
3. **Gates G1 to G10, original against original:** B restored original decisions next to dev-c4 restored original decisions (Section 2b), same layout.
4. **Per-class G3:** correct / n for corrupt_file, decoder_incompatible, identity_mismatch, metadata_naming, order_edition_ambiguity, healthy (and the G4 abstention share for insufficient_evidence), guarded and original, B next to dev-c4, with the classes below 2/3.
5. **Guard effect:** unsafe proposals hidden by the guards (a guard-changed original write that score.py's rule counts unsafe), all hidden writes, every guard-made escalation (case, rule, original class/action, whether the original and the final were correct), G1 on guarded against original decisions.
6. **Validity:** first-attempt valid, repaired, forced, protocol violations, repair prompts, rejected write attempts (`g1_context`).
7. **Context (qwen):** turns and cases flagged, and the subset row of section 3. **Failures and partial runs** stay in the tables as "started-aborted", "never started" or "forced", never dropped.
8. **Statements, verbatim in the report:** dev-tuned; one pass on correlated, previously tuned fixtures; neither significance nor generalisation; no readiness claim; B is a combined candidate so an effect is not attributable to the prompt or to the format; dev-c4 differs in prompt, evidence format, guards version and harness fixes; G6 measures fixture verification, not completed repairs.
G2, G3 per class, G4 and G5 are of interest and are not targets. No other table, cut, ranking or threshold is added after the results.
